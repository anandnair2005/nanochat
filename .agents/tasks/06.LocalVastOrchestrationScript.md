# Task 06: Implement Local Vast Orchestration Script

## Status
Implemented; real paid Vast operations not executed.

## Completion Notes
- Created `tasks/vast_orchestrate.py`.
- Added `.agents/runs/` to `.gitignore` for local manifests.
- Script loads local `.env` without committing credentials, including SSH key file paths.
- Supports `plan`, `prewarm`, `launch-h100`, and `cleanup` subcommands.
- `plan --dry-run` writes a manifest and performs no paid actions.
- `prewarm` searches offers, requires exactly one existing Vast volume, shows selected offer/volume, requires explicit `yes` confirmation unless `--yes` is supplied, creates only the prewarm instance, records IDs immediately, injects local SSH public key by env var, copies local rclone config over SSH, and starts `runs/prewarm_vast.sh` in detached tmux.
- Revised volume behavior: the orchestrator now assumes at most one Vast storage volume. It reuses the existing volume only if its size is at least the requested storage size, errors if it is too small or size cannot be determined, and creates a new volume of the requested size when none exists.
- Prewarm now uses a separate default image `python:3.10-slim-bookworm` instead of the H100 app image. The orchestrator launches it in Vast SSH mode, installs minimal tools via on-start (`curl`, `git`, `openssh-client`, `rclone`, `rsync`, `tmux`), attaches the configured public SSH key, rsyncs the repo from local checkout, injects local rclone config, and runs prewarm with `NANOCHAT_UV_EXTRA=cpu`.
- `runs/prewarm_vast.sh` now supports `NANOCHAT_UV_EXTRA`, defaulting to `gpu` for backward compatibility but allowing CPU-only prewarm dependency setup.
- `launch-h100` does not create or choose an H100; it requires exactly one running H100 instance, copies local rclone config over SSH, passes runtime env including `WANDB_API_KEY` when enabled, and starts `runs/speedrun_vast.sh` in detached tmux session `nanochat-$NANOCHAT_RUN_ID`.
- `launch-h100` now infers GPU count from Vast instance metadata and passes `NANOCHAT_NUM_GPUS`; `--num-gpus` can override inference for 4xH100, 8xH100, or small smoke-test instances.
- `cleanup` reads the manifest and is idempotent/dry-run-capable; it refuses cleanup before a `final_sync_complete` manifest event unless `--force` is supplied.
- Local validation passed: Python compile, `--help`, `plan --dry-run`, cleanup dry-run with force, shell syntax checks, and H100 launch refusal when zero running H100 instances are visible.
- Current Vast account check during implementation showed zero running instances and zero volumes. Dry-run prewarm successfully selected candidate storage and prewarm offers without creating paid resources; real prewarm creation and H100 SSH/tmux launch were not executed.
- Agreed default config values: image `anandnair2005/nanochat-vast:h100`, run ID `d24`, storage size `150 GB`, base checkpoint interval `200`, retain latest `3` local checkpoints after successful sync, wandb enabled, rclone remote `nanochat_gdrive_runner:`.

## Agent Objective
Implement a local script that controls the Vast workflow: create/confirm only the prewarm instance, use the single existing storage volume, wait for the user-created H100 instance, start the workload over SSH/tmux, monitor status, sync artifacts, perform cleanup, and preserve a manifest.

## Files To Create Or Modify
- Create `tasks/vast_orchestrate.py` or `tasks/vast_orchestrate.sh`; prefer Python if using JSON manifests and API polling.
- Create a sample config file such as `tasks/vast_orchestrate.example.json` if needed.
- Do not include real Vast API keys or personal account data.
- Do not hardcode offer IDs, machine IDs, or Google Drive paths.

## Required Behavior
- Support `--dry-run` that performs no paid Vast actions.
- Support `--run-id`.
- Support `--image` for the custom Docker image tag.
- Support `--manifest` path, defaulting to `.agents/runs/<run-id>/manifest.json` or similar.
- Support prewarm offer selection and show cost/details before asking for explicit confirmation.
- Do not create, price-filter, or choose the H100 instance.
- Poll Vast running instances and use the single running H100 instance once it appears.
- Assume exactly one storage volume exists in the Vast account; fail clearly if zero or multiple volumes exist.
- Support a cleanup subcommand or mode that reads a manifest and destroys resources.
- Store every created instance ID and storage/volume ID in the manifest immediately after creation.
- Label resources with the run ID where the Vast API/CLI supports labels.
- Poll instance state and detect bad terminal states such as `exited`, `unknown`, and `offline`.
- Treat completion markers as success signals only after final sync has completed.
- Require explicit confirmation before creating the paid prewarm instance unless `--yes` is supplied.
- Start H100 training over SSH in a named tmux session after the manually created H100 instance is running.

## Implementation Constraints
- Prefer the Vast CLI or SDK if available; if not, use REST API with `VAST_API_KEY` from the local environment.
- Keep credentials local. Do not pass broad Vast API keys into the training container.
- Copy or inject the rclone configuration to the active Vast instance at runtime over SSH; do not bake it into the Docker image.
- Pass `WANDB_API_KEY` to the H100 training tmux command from the local orchestrator over SSH when wandb is enabled; do not bake it into the Docker image or require pre-login inside the image.
- The first implementation may support dry-run and manifest/cleanup scaffolding before real API launch if Vast credentials are unavailable.
- Make cleanup idempotent.
- Do not destroy resources if final artifact sync failed unless a force flag is provided.

## External Tools Required
- `VAST_API_KEY` in the local environment for real runs.
- Vast CLI, Vast SDK, or HTTPS access to the Vast REST API.
- SSH client may be needed if running commands on instances through SSH.
- Local rclone configuration is needed so the orchestrator can provide it to prewarm/H100 instances at runtime.
- `jq` is useful if implementing in shell.
- A Vast MCP server or Vast CLI skill would significantly help this task by simplifying offer search, launch, logs, and cleanup. If unavailable, implement against the CLI/API.
