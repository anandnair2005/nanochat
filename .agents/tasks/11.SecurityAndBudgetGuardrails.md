## Agent Objective
Add explicit safeguards to the Vast speedrun tooling so agents cannot accidentally leak secrets, create paid prewarm resources without confirmation, or leave expensive resources running without clear recovery paths.

## Files To Create Or Modify
- Modify `tasks/vast_orchestrate.py` or equivalent orchestration script.
- Modify Docker-related files only to improve secret exclusion.
- Create `docs/vast_security_budget.md` if detailed documentation is needed.
- Do not commit any real secrets.

## Required Behavior
- Refuse prewarm instance creation without showing offer/cost details and receiving explicit confirmation unless `--yes` is supplied.
- Do not create H100 instances or enforce H100 price limits; H100 cost decisions are made manually by the user.
- Support max runtime or timeout settings for prewarm and H100 phases.
- Write a manifest immediately after each resource is created.
- Provide a command to list or identify active resources associated with a run ID if supported by the Vast tooling.
- Redact known secret names from logs and dry-run output.
- Ensure `.dockerignore` excludes `.env`, rclone configs, wandb files, datasets, checkpoints, local manifests, and caches.
- Document where secrets should live: local env for Vast API, Vast encrypted env vars or mounted files for rclone/wandb.
- Document the selected secret flow: Vast API key remains local; SSH private key remains local; rclone config is copied/injected at runtime; `WANDB_API_KEY` is passed by the local SSH orchestrator; Docker image contains no secrets.

## Implementation Constraints
- Do not implement custom secret storage.
- Do not print all environment variables.
- Do not pass local `VAST_API_KEY` into the training container unless the user explicitly requests self-destruction behavior.
- Do not bake or persist `WANDB_API_KEY` in the image; pass it only to the tmux training command environment when wandb is enabled.
- Do not bake or persist rclone OAuth tokens in the image; copy/inject them only at runtime and rely on instance/storage destruction after final sync.
- Keep force flags explicit and scary in help text.

## External Tools Required
- No external tools are required for local guardrail implementation.
- Vast CLI/API is required to validate active resource listing.
- Secret scanning tools such as `gitleaks` would help if available, but are optional.
- A security-focused MCP is not required.

## Commands To Run
- Run orchestrator help and dry-run commands to confirm guardrails appear in usage.
- Run a dry-run without prewarm cost confirmation and confirm it refuses to create the prewarm instance.
- Run a dry-run without confirmation and confirm it refuses paid launch.
- If `.dockerignore` changed, inspect it manually and include the relevant exclusions in the final response.

## Acceptance Criteria
- Prewarm launch paths require cost display and confirmation.
- H100 launch paths are absent; the orchestrator only discovers and uses the single running H100 instance.
- Secret-like values are not printed in normal output.
- Docker build context excludes secrets and large generated artifacts.
- Timeout and cleanup recovery options are documented or implemented.
- The final agent response lists the guardrails added and any guardrails still requiring live Vast validation.

## Stop And Ask If
- The user wants self-destruction from inside the container using Vast API credentials.
- A live resource scan is required but no Vast API key is available.
- The user wants to store secrets in repo files.
